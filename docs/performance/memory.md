## 2026-10-09の調査: #29で増えた原因と修正

ワークスペースを開いた時に全ファイルの索引を読み、Svelteの`$state`で持つようになったことが原因だった。#29のサイドバーで追加した。`index`と`trashItems`を`$state.raw`へ変えて直した。機能の動きは変えていない。

### 測定条件

本物のMacアプリを測定用の名前(Nagori QA Mem、識別子app.nagori.editor.qa20261004)でビルドし、macOSのfootprintでアプリ全体(WebContentを含む)を測った。ワークスペースは991個のMarkdownと10個の画像、計1,000ファイル。各場面は30秒待ってから5秒おきに6回測り、中央値を使った。合計は測るたびに揺れるため、WebContentのWebKit mallocと使用中(dirty)で比べた。

### 増加の測定(修正前)

### 原因

#29のApp.svelteは、ワークスペースを開く時に`workspace_index`で全ファイルの索引を読む。#28までは、索引を読むのはCmd+Pの時だけだった。読んだ索引は`$state`で持ち、`allNotes`・`starredNotes`・`recentlyEdited`と件数を`$derived`で作る。

Svelte 5の`$state`は配列の要素ごとにProxyとシグナルを作る。索引は約1,000件あるため、WebKit側で多くのオブジェクトが増えたと考えた。`index`は要素を書き換えず、毎回丸ごと置き換えるだけなので、raw状態にしても動きは変わらない。

Nodeでの確認も行った。`allNotes`と`recentlyEdited`を1000件で200回呼んでも、GC後に残るヒープはほぼゼロだった。V8の数値なので、WebKitの原因の確定には使っていない。

### 直し方

`src/App.svelte`で次の2つを`$state.raw`へ変えた。

- `index`: `let index = $state.raw<Entry[]>([])`
- `trashItems`: `trashItems = $state.raw<TrashItem[]>([])`

`index`と`trashItems`を要素ごとに書き換える箇所はない。変更は再代入だけなので、`$derived`の再計算の条件も変わらない。コメントで、丸ごと置き換えるだけのためrawにしたことを書いた。

### 残る課題と判断した点

CodeMirrorの全文装飾、構文木、PreviewContextが持つ本文の参照、AppのinitialText、EditSession.textを確認した。文字列の重複は候補だが、100KiBの文字列を複数持つことだけで数十MiBの差を説明できるとは確認していない。保存、外部変更、競合、Undoに関わる保持を推測で削らない判断とした。

MathJaxは既にMathDocument.clear、output.clearCache、現在の記事のdocument・math・table等への参照解除を行っている。画像側も記事変更時のBlob URL解放と、古い非同期結果の破棄を行っている。コード上で解放処理があることと、WebKitが物理メモリを返すことは別に検証する必要がある。フォントやDOM、レイアウト、解放後の割当領域のどれが残るかは特定できていない。

次はQAアプリの重複がない状態で、WebContentのヒープとDOM・フォント保持を調べる必要がある。全文装飾を減らす案は、Nodeの保持量だけで採用せず、数式とPreviewモードも含む実機比較が必要。今回、数式抽出の差分解析は試していない。
